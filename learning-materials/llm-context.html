③ 结构化解释

我对"上下文"的理解

💡 我的理解一句话：上下文是模型在某次推理时，同时"看在眼里"的那段文本——包括用户的问题、历史对话、粘贴的文档、工具返回的结果。它是模型的"临时工作记忆"，决定了模型这一次到底能利用哪些信息。

核心组成：上下文窗口

上下文窗口是一段有限容量的输入区，用 token（词元）计量。每次向模型发送的内容 + 模型要生成的回复，都必须装进这个窗口里。

  ┌────────────────────────────────────────┐
  │           上下文窗口 (context window)          │
  ├──────────────┬──────────┬──────────────┤
  │ 前置信息     │  用户/提示  │  模型回复       │
  │ (system,    │ (prompt,  │ (response,   │
  │  历史对话)   │  本次输入)  │  生成部分)     │
  └──────────────┴──────────┴──────────────┘
         ↑ 总量受 token 上限约束，超出则截断/报错

它由什么组成

  • System 提示：系统性约束（身份、规则）。
  • 历史对话：之前的多轮消息。
  • 本次输入：用户新消息、粘贴的文档。
  • 工具结果：Agent 调用工具后返回的数据。
  • 待生成部分：模型将要输出的内容也要占用窗口。

关键真相：长 ≠ 好用

研究《Lost in the Middle》发现，模型对上下文信息的利用并不均匀：

  • 放在开头和结尾的信息，最容易命中。
  • 放在中间的信息，即使模型号称"支持长上下文"，也更容易被忽略（性能显著下降）。
⚠️ 所以实战中：重要信息要么放最前（system/开头），要么放最后；不要指望把关键内容埋在长文档中间——这与直觉相反，是最容易踩的坑。
④ 应用案例

一个具体场景：交给 Agent 一份 50 页合同

假设你让 Agent 审核一份长合同，这正好暴露"上下文"的取舍：

  1. 合同全文塞进上下文 → 可能撑爆窗口，或让关键条款"迷失在中间"。
  2. 更稳的做法：先检索（RAG）出和"违约责任"相关的那几段，只把最相关的段落 + 你的问题放进去。
  3. 关键结论放上下文末尾（贴近提问），让模型更容易命中。

这正是"上下文工程"的意义：不是塞更多，而是塞得准、放对位置。

⑤ 概念辨析

容易混淆的地方

混淆项它 ≠ 什么边界在哪
上下文 vs 长期记忆上下文不是"记住的所有事"上下文=当前这次推理可见的临时输入；记忆=跨会话持久保存的状态
上下文长度 vs 有效利用窗口大 ≠ 模型善于用长内容中间易丢失，需把关键信息放头/尾或先检索
上下文 vs 提示（prompt）prompt 只是上下文的一部分prompt=你写的指令；上下文=含 prompt、历史、工具结果在内的全部输入
上下文 vs 训练数据不是模型"学过的一切"训练数据是模型参数里的知识；上下文是每次对话临时注入的
⚠️ 使用边界：上下文是易失的、有容量上限的。要记住的事实应落到"记忆"或外部存储（如文件、数据库），不能只依赖上下文。
⑥ 自测问题

检验是否真懂

Q1 什么是上下文窗口，用什么计量？
✔ 模型单次推理可见的输入区，用 token 计量，有容量上限。
Q2 《Lost in the Middle》的核心发现是什么？
✔ 模型对上下文开头和结尾的信息利用最好，中间的信息最容易被忽略，即使支持长上下文。
Q3 上下文和"长期记忆"有什么不同？
✔ 上下文是当前推理的临时输入，易失；记忆是跨会话持久保存的状态。
Q4 给 Agent 塞长文档时，关键信息应该怎么放？
✔ 放开头或末尾，或先用检索筛出最相关段落，避免埋在长内容中间。
