③ 结构化解释

我对 Skill 的理解

💡 我的理解一句话：Skill 是把「一件我经常要做的、有固定方法的事」沉淀成一份规范性文档，让 AI 下次遇到同类任务时照着做，不用我每次重新教一遍。它本质上是一种可复用、可积累的任务知识。

Skill 解决什么问题

假设你经常要"生成一份学习资料"：

  • 没有 Skill：每次都要重新描述"要哪些模块、怎么组织、来源怎么核查"——又长又容易漏。
  • 有了 Skill：把这些要求写进一个 Skill，之后只需说"用这个 Skill 学一下 XX"，AI 自动按流程走。

一个 Skill 由什么组成（以本作业为例）

本作业目录 .workbuddy/skills/concept-learning-generator/SKILL.md 就是一个典型 Skill：

组成部分作用本项目的例子
YAML 元数据声明名字 + 用途，供系统识别与调用name / description
适用场景说明"什么时候该用我"想快速吃透一个陌生概念时
输入信息说明需要用户提供什么概念名 + 可选背景/难度
生成步骤 / 输出结构规定产出什么、按什么格式7 大模块 → HTML
资料来源要求 + 自检约束真实性与质量来源必须可核查，禁止伪造

Skill 是如何被"执行"的（我的理解）

  你：用 XX Skill 学习「概念」
        ↓
  ① 系统读取 .workbuddy/skills/XX/SKILL.md
        ↓
  ② 把 SKILL.md 里的规范「注入」给 AI（成为上下文的一部分）
        ↓
  ③ AI 按里面的步骤/结构/自检要求执行
        ↓
  ④ 产出符合规范的成果（本例=一份 HTML 学习资料）

注意：Skill 本身是静态文档 + 触发机制，真正的"智能"由背后的 AI（Agent）承担——这正是三份资料的联动点。

⚙️ 关键点：一个好的 Skill 要通用、可复用。它描述的是"一类任务的通用方法"，而不是"某一次正好这样写"——所以它能接住任意新概念、新任务，而不是写死成一次性提示词。
④ 应用案例

一个具体场景：把"生成学习资料"变成 Skill

在 WorkBuddy 里：

  1. 我在仓库里建了 concept-learning-generator 这个 Skill。
  2. 下次我说"帮我把这个 Skill 生成的学习资料做成网页"，或"用这个 Skill 学一下 Transformer"。
  3. AI 读到 SKILL.md → 按 7 大模块 + 真实来源 + 自检要求，自动产出对应学习资料。

价值：一次沉淀、反复使用。同样的流程无论学"Agent"还是"Transformer"都成立，无需重写。

⑤ 概念辨析

容易混淆的地方

混淆项它 ≠ 什么边界在哪
Skill vs 一次性提示词Skill 不是"这次跟我说的那句话"提示词是一次性的；Skill 是可复用、可沉淀的规范文档
Skill vs 工具(Tool)Skill 不是外部函数/API工具是能调用的外部能力；Skill 是"怎么做某类事"的方法论
Skill vs 上下文Skill 不是执行时的临时输入Skill 是持久资产；上下文是某次推理临时注入的输入。真要用 Skill，需要把它的内容放进上下文才能生效
Skill vs 文档/知识库Skill 不只是资料Skill 强在可执行的方法流程；纯知识库偏信息，Skill 偏"怎么做"
⚠️ 使用边界：Skill 要可持续复用才有价值，一件事只做一次就不必做成 Skill。它依赖背后有能读懂并执行它的 AI（Agent），且运行时要借助上下文承载。
⑥ 自测问题

检验是否真懂

Q1 Skill 本质上是"什么东西"？
✔ 把一类可复用任务的方法沉淀成规范文档，让 AI 下次照着做。
Q2 一个 Skill 文件通常有哪两大部分？
✔ YAML 元数据（name/description）+ 正文规范（场景/输入/步骤/输出/来源/自检）。
Q3 为什么说 Skill 是一次性的提示词不够用？
✔ 提示词每次都要重写、容易遗漏；Skill 一次沉淀、反复复用，且可校准更新。
Q4 在 WorkBuddy 里，Skill 需要放进哪里才能被执行？
✔ 需放进 AI 的上下文（运行时被读取/注入）才能生效；静态存在磁盘上只是待用资产。
