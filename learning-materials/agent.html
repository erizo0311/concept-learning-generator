③ 结构化解释

我对 Agent 的理解

💡 我的理解一句话：Agent 是让大模型自己决定下一步做什么的 AI——它根据目标、环境和工具反馈，动态地规划、调工具、看结果、再调整，直到完成任务，而不是按人写死的路径一步步走。

核心区别：Workflow vs Agent

Anthropic 官方把这类系统分成两条路线，这是我理解 Agent 的关键入口：

类型谁来决定路径特点适合
Workflow（工作流）人预先写好的代码可预测、稳定、可控路径明确的固定任务
Agent（智能体）大模型动态决策灵活、自适应、能处理意外开放性、无法硬编码路径的任务

Agent 的四段循环（我的简化模型）

  ┌─────────────┐
  │ ① 感知 (Perceive)  │  接收目标 + 当前环境/上下文
  └──────┬──────┘
         ↓
  ┌─────────────┐
  │ ② 规划 (Plan)     │  拆解目标 → 形成行动步骤
  └──────┬──────┘
         ↓
  ┌─────────────┐
  │ ③ 行动 (Act)      │  调用工具(搜索/代码/API)执行
  └──────┬──────┘
         ↓
  ┌─────────────┐
  │ ④ 反思 (Reflect)  │  观察结果 → 判断是否达成 / 修正
  └──────┬──────┘
         ↓
        ↺ 回到 ②，直到完成

它由什么组成

  • 大模型大脑：负责推理、规划、决定调哪个工具。
  • 工具（Tools / ACI）：搜索、读文件、写代码、调 API——模型能否"做事"靠它们。
  • 环境反馈：工具返回的结果，驱动下一步决策。
  • 上下文窗口：承载目标、历史步骤、工具结果——是 Agent 的"工作记忆"（详见第 2 份资料）。
  • 记忆（可选）：跨会话/长任务保存状态。
⚙️ 关键点：Anthropic 强调"简单至上"——真正好用的 Agent 往往只用几个简单的可组合模式，而不是套一个庞大框架。它同时提醒：工具接口（ACI）要像设计人机界面一样用心设计，工具文档写得越清楚，模型越会用。
④ 应用案例

一个具体场景：AI 编程助手

想象一个"自动修 bug"的 Agent：

  1. 你丢给它一句"这个 Python 脚本报错了，帮我修好"。
  2. 感知：它读取错误堆栈 + 相关代码文件。
  3. 规划：判断可能是变量名错误，决定"先读这一行的上下文，再搜索该函数的定义"。
  4. 行动：调用工具——读文件、用 grep 搜索、甚至跑一遍测试。
  5. 反思：看到测试变绿，确认问题解决；如果还报错，就回到规划换一种思路。

过程完全由模型自主推进，无需你提前写清每一步——这正是 Agent 的价值：开放性任务、路径不确定。

⑤ 概念辨析

容易混淆的地方

混淆项它 ≠ 什么边界在哪
Agent vs 工作流不是所有 AI 功能都是 Agent路径由谁定：人写死=工作流，模型定=Agent
Agent vs 机器人/RPA不是"会自动化"就是 AgentRPA 按固定脚本操作；Agent 靠推理动态决策
Agent vs 普通对话不是能聊天就叫 AgentAgent 会调用工具、采取行动并基于反馈迭代；对话只是输出文字
"全自主"误区不是 Agent 就该无人监督现实里常需人工介入/暂停点（human-in-the-loop）
⚠️ 使用边界：任务简单、步骤固定时，强行上 Agent 只会增加成本、延迟和不可控风险。Anthropic 的原话是"从最简单的开始，复杂了再逐步加"。先工作流，后 Agent。
⑥ 自测问题

检验是否真懂

Q1 一句话说明 Workflow 和 Agent 的本质区别。
✔ 区别在"谁决定路径"：Workflow 由人写死的代码决定，Agent 由模型根据上下文动态决策。
Q2 Agent 的典型四段循环是什么？
✔ 感知→规划→行动→反思，循环往复直到完成。
Q3 什么信号说明"这个任务确实该用 Agent"？
✔ 任务开放式、路径无法硬编码、需要模型不断调工具并依据反馈修正。
Q4 "AI 会聊天的界面就是 Agent"——对还是错？
✔ 错。Agent 必须能调用工具、采取行动并依据反馈迭代，仅输出文字不构成 Agent。
